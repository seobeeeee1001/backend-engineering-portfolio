## 1. 예약 당시의 약속을 보존하는 데이터 모델

**SnapBook · Java / Spring Boot / JPA / MySQL**

- **문제·판단:** 메뉴 설정이 바뀌어도 기존 예약의 가격과 확정된 소요시간은 보존해야 합니다. 현재 메뉴와 개별 예약의 정보를 구분했습니다.
- **구현:** 예약 메뉴명·가격을 스냅샷으로 저장하고, 소요시간은 예약에 보관했습니다. 예약 변경과 시스템 메시지를 같은 트랜잭션에 저장하고 커밋 후 WebSocket으로 발행했습니다.
- **검증:** 메시지 저장 실패 시 예약 롤백, 발행 실패 시 저장된 예약·메시지 유지 조건을 통합 테스트로 명시했습니다.

## 2. 결제 승인과 이용권 지급 사이의 실패 복구

**한능검 학습 서비스 · TypeScript / PostgreSQL / Toss Payments**

- **문제·판단:** 외부 승인 성공과 내부 DB 저장 성공은 다릅니다. 승인 요청 사실을 먼저 남기고 결제사 재조회로 누락된 지급을 복구하도록 했습니다.
- **구현:** 주문별 중복 지급과 환불 후 재지급을 차단했습니다. 운영에서 주문번호 조회 404와 결제 키 조회 200을 대조해 조회 경로를 수정하고, 같은 404도 승인 요청 여부에 따라 처리했습니다.
- **검증:** 별도 PostgreSQL 16에서 결제사 모의 응답과 DB 저장 실패를 사용해 이용권이 한 번만 복구되는지 확인했습니다. PGlite에서는 다른 주문의 결제 키를 거절하는 조건도 검증했습니다.

[복구 흐름과 오류 판단 기준 →](cases/02-payment-recovery.md)

## 3. 기기 변경·중복 전송에도 유지되는 계정별 진도

**한능검 학습 서비스 · TypeScript / PostgreSQL**

- **문제·판단:** 브라우저에만 남던 기록을 계정별 DB로 옮기면서, 전체 덮어쓰기 대신 변경의 성격에 따라 합산·중복 제거·삭제 보존 규칙을 정했습니다.
- **구현:** 변경 UUID와 처리 기록, 사용자·진도 행 잠금, 삭제 revision을 적용했습니다. 계정별 미전송 변경을 재시도하고 이전 계정의 늦은 응답을 차단했습니다.
- **검증:** 12개 변경을 각각 두 번 동시 요청해 12개만 반영하는 PostgreSQL 테스트와, 삭제 후 오래된 요청이 기록을 되살리지 않는 검증을 구성했습니다. 후속 PR에서 별도 PostgreSQL 실행 통과를 기록했습니다.

[충돌 규칙과 검증 시나리오 →](cases/03-progress-sync.md)

## 4. 집계 의미를 유지한 SQL 개선

**한능검 운영 관리 화면 · SQL / PostgreSQL**

- **문제·판단:** 관리자 탭이 열리지 않는 현상을 행동 집계 쿼리 지연으로 좁혔습니다. 같은 방문자의 행동과 로그인 후 다른 기기의 행동을 함께 세는 의미를 유지해야 했습니다.
- **구현:** `OR`·상관 서브쿼리 결합을 두 등호 결합과 `UNION ALL`로 분리하고, 최종 `COUNT(DISTINCT)`로 중복 집계를 막았습니다.
- **검증:** 기존 집계 테스트를 유지했습니다. 방문자 100명·이벤트 2,500건의 합성 데이터로 메모리 PGlite에서 비교한 실행 시간은 **294초 → 0.45초**입니다. 운영 PostgreSQL 실측과는 구분합니다.
