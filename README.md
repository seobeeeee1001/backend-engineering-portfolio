## 1. 메시지의 저장 결과와 화면 표시 일치

**SnapBook · Java / Spring Boot / MySQL / WebSocket**

상담과 예약을 하나의 채팅방에서 진행하는 서비스입니다. 배포 중 서버가 종료될 때 화면에는 전송됐다고 표시되지만 DB에는 메시지가 없거나, 저장은 됐는데 결과를 받지 못해 재시도할 수 있었습니다.

- **판단:** Graceful Shutdown만으로는 서버에 도착하지 않은 메시지를 보호할 수 없어, DB 저장 결과를 확인한 뒤에만 전송 완료로 표시하도록 했습니다.
- **구현:** 결과를 받지 못하면 저장 여부 미확인 상태로 알리고 같은 메시지 ID로 재시도합니다. 서버는 이미 저장한 메시지의 결과를 반환하며, 재접속 후 이력을 조회해 화면을 복구합니다.
- **검증:** 격리된 Docker 환경에서 서버 수신 전·DB 커밋 전·커밋 후 결과 수신 전을 각각 3회 검증했습니다. 개선 후 9회 모두 재시도·복구 뒤 DB와 발신자 화면에 **메시지 1건**이 유지됐습니다.

## 2. 결제 실패 복구와 주문별 이용 기간 보존

**한능검 유료 학습 서비스 · TypeScript / PostgreSQL / Toss Payments**

외부 결제 승인은 내부 DB 트랜잭션과 함께 롤백되지 않습니다. 승인 후 이용권 저장이 실패해도 복구할 수 있어야 하며, 환불할 때는 별도로 구매한 이용 기간을 지켜야 했습니다.

- **승인 복구:** 승인 요청 사실과 결제 키를 먼저 저장합니다. 결제사 재조회 결과의 주문번호·금액을 대조하고, 주문을 잠근 뒤 지급 여부를 다시 확인해 이용권을 한 번만 지급합니다.
- **환불 처리:** 주문별 이용 기간을 기록하고 환불 주문의 미사용 기간만 제거합니다. 3일권 환불 시 별도로 구매한 하루 연장은 보존하고, 늦은 승인 결과로 환불 주문을 다시 지급하지 않습니다.
- **검증:** 별도 PostgreSQL 16에서 결제사 응답을 모의하고 승인 직후 DB 저장을 강제로 실패시켰습니다. 재조회 후 한 번만 복구되는지, 반복 환불 통보에도 다른 구매의 기간이 유지되는지 확인했습니다.
