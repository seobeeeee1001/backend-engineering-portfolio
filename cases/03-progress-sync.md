# 계정별 진도와 중복·충돌 처리

[← 전체 사례](../README.md)

**프로젝트:** 한능검 학습 서비스

**맡은 범위:** 계정별 서버 저장·복원, 변경 단위 동기화, 클라이언트 재시도와 계정 전환 처리

## 문제와 판단

진도가 브라우저 저장소에만 있으면 다른 기기에서 이어서 학습하기 어렵고, 같은 기기에서 계정을 바꿀 때 기록이 섞일 수 있습니다. 사용자별 DB를 정본으로 두되, 기기의 전체 상태를 덮어쓰면 다른 기기의 최신 풀이와 삭제가 사라질 수 있다고 판단했습니다.

변경마다 UUID와 기준 revision을 붙이고, 같은 요청의 재전송인지 독립적인 새 변경인지 구분했습니다. 처리 기록(receipt)과 진도 변경은 같은 트랜잭션에 저장했습니다.

## 변경의 의미에 따른 규칙

| 상황 | 규칙 | 지키려는 결과 |
| --- | --- | --- |
| 같은 UUID·같은 본문 재전송 | 이미 처리한 변경은 다시 적용하지 않음 | 응답 유실 후 재시도해도 풀이 수 유지 |
| 같은 UUID·다른 본문 | 충돌로 거절 | 요청 식별자를 재사용한 다른 변경 차단 |
| 독립적인 풀이가 동시에 도착 | 사용자·진도 행 잠금 후 각각 합산 | 한쪽 풀이가 덮어써지지 않음 |
| 삭제 전 revision의 변경 도착 | 삭제 revision을 보존해 오래된 변경 차단 | 삭제한 북마크·기록의 부활 방지 |
| 계정 전환 후 이전 요청 응답 도착 | 계정별 대기 변경과 응답 적용 경계 분리 | 다른 계정의 화면·기록 오염 방지 |
| 학습 계획을 여러 기기에서 확정 | 먼저 저장한 날짜별 구성을 유지 | 기기마다 하루 학습 구성이 달라지지 않음 |

서버 잠금은 사용자 행을 먼저, 진도 행을 다음 순서로 획득합니다. 클라이언트에는 계정별 미전송 변경을 보관하고 네트워크 복구·포커스 복귀 시 재시도하도록 했습니다.

학습 계획 저장을 확장할 때는 모의고사 결과의 시각을 비교해 과거 결과가 최신 결과를 덮어쓰지 않도록 했습니다. 이 시각 규칙을 모든 종류의 시험 결과에 일괄 적용한 것은 아닙니다.

## 검증

PostgreSQL 동시성 테스트는 12개의 독립적인 풀이 변경을 각각 두 번씩, 총 24회 동시에 요청합니다. 기대 결과는 정답 6회·오답 6회와 처리 기록 12개입니다. 이어 북마크를 삭제하고 삭제 전 revision을 가진 추가 요청 8개를 동시에 보내, 삭제 상태가 유지되는지 검사합니다.

API·클라이언트 자동 테스트에는 응답 유실 후 재전송, 같은 UUID의 본문 변조 거절, 계정 전환과 늦은 응답도 포함했습니다. 초기에는 별도 PostgreSQL 실행이 보류되었으며, 후속 검증에서 PostgreSQL 16 전용 테스트 통과를 확인했습니다.

## 적용 범위

초기의 옛 브라우저 진도 가져오기는 후속 변경에서 중단됐습니다. 서버 정본과 현재 계정의 미전송 변경 처리는 유지됩니다. 이후 추가한 학습 계획 가져오기는 별도 기능이며, 기존 서버 값을 우선하고 중복 적용 결과가 같도록 구성했습니다.
